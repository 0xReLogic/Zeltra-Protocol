# BLS Signature Generation Guide

## Overview

This guide explains how to generate valid BLS signature test data for the Nimbus spend transaction testing.

## What is BLS Signature?

BLS (Boneh-Lynn-Shacham) is a cryptographic signature scheme used in the Nimbus protocol for anonymous spending. The contract verifies BLS signatures using the EIP-2537 pairing precompile.

## BLS Signature Components

The `spend` function requires the following BLS signature parameters:

- `nullifier`: bytes32 - Hash of the message (32 bytes)
- `alpha_neg_hex`: bytes - Negative alpha point in G1 (128 bytes, EVM format)
- `hm_hex`: bytes - Hash-to-curve point H(m) in G1 (128 bytes, EVM format)
- `pk_iss_hex`: bytes - Issuer public key in G2 (256 bytes, EVM format)

## EVM Format Requirements

The contract expects BLS points in EVM big-endian format:

### G1 Points (128 bytes)
- X coordinate: 64 bytes (big-endian, padded with 16 leading zeros)
- Y coordinate: 64 bytes (big-endian, padded with 16 leading zeros)

### G2 Points (256 bytes)
- X1, X0, Y1, Y0: each 64 bytes (big-endian, padded with 16 leading zeros)
- Order: X1, X0, Y1, Y0 (different from arkworks default order)

## Generate BLS Test Data

### Using the Example Program

Run the BLS signature generation example:

```bash
cargo run --package nimbus-core --example generate_bls_test_data
```

This will output:
- Nullifier hex
- alpha_neg_hex (G1 point)
- hm_hex (G1 point)
- pk_iss_hex (G2 point)
- A curl command to test the spend endpoint

## Important Notes

### For Testing Only
The generated BLS signature data is for testing purposes only. It uses randomly generated keys and messages, not actual signing from the issuer.

### For Production
In production, BLS signatures must be generated by the actual issuer using their secret key. The signature must satisfy the pairing equation:
```
e(alpha, pk_iss) == e(H(m), G2)
```

### Contract Verification
The contract verifies signatures using the EIP-2537 pairing precompile at address 0x0f. The verification checks:
1. The pairing equation holds
2. The nullifier hasn't been spent before
3. The contract has sufficient USDC balance

## Troubleshooting

### Transaction Fails on Chain
If the transaction broadcasts successfully but fails on-chain with status FAILED:
1. Check if the contract has USDC balance
2. Verify the BLS signature format is correct (EVM big-endian)
3. Ensure the nullifier hasn't been spent before

### Gas Cost
Gas cost is now dynamic and fetched from the blockchain using RPC with fallback support. The system automatically switches to the fallback RPC if the primary fails.
