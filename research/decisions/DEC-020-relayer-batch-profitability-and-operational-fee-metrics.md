# DEC-020: Relayer Batch Profitability & Operational Fee Metrics

## Status
Accepted

## Date
2026-10-03

## Context
The Nimbus relayer batches private spend transactions (2 to 8 items) to amortize base transaction execution overhead on Arbitrum Stylus and generate relayer fee profit. In [`DEC-006`](file:///workspaces/Zeltra-Protocol/research/decisions/DEC-006-adaptive-private-spend-batching.md), an adaptive batching mechanism and SQLite table `spend_batches` were established.

However, the relayer's health monitoring endpoint (`/api/health`) and operator telemetry lacked summarized visibility into batch profitability and efficiency metrics:
1. **Total Batch Count (`batch_count`):** How many aggregated batches the relayer has settled on-chain.
2. **Cumulative Profit Margin (`total_batch_margin_usdc`):** The net revenue generated by the relayer after accounting for on-chain L1/L2 gas consumption.
3. **Average Batch Size (`avg_batch_size`):** The average number of transactions bundled per on-chain batch, measuring batching efficiency against the 2–8 item window.
4. **Execution Fee Claims (`total_claimed_fees_usdc` & `unclaimed_fees_usdc`):** Financial health of accrued execution fee liabilities owed by the contract to the relayer.

## Precedents & Industry Standards (2024–2026)
- **Arbitrum & L2 Rollup Economics (growthepie / Dune Analytics):** L2 and cross-chain relayers (Across, Connext, Hop) measure profitability as `net_profit = fees_collected - l1_l2_gas_costs`. Monitoring average batch size indicates whether batching delays are optimal or leading to timeout-induced small batches.
- **Relayer Observability Best Practices:** The `/health` or `/metrics` endpoint serves automated liveness probes and telemetry scrapers (Datadog/Prometheus), requiring lightweight aggregates directly from persistent storage without expensive full table scans.

## Decision

### 1. Database Batch Metrics Query (`get_batch_metrics`)
Add a dedicated query function on [`Database`](file:///workspaces/Zeltra-Protocol/nimbus-node/src/database.rs) that calculates:
```rust
#[derive(Debug, Clone, Serialize, Deserialize, Default, PartialEq)]
pub struct BatchMetrics {
    pub batch_count: i64,
    pub total_batch_margin_usdc: f64,
    pub avg_batch_size: f64,
    pub total_execution_fees_usdc: u64,
    pub claimed_execution_fees_usdc: u64,
    pub unclaimed_execution_fees_usdc: u64,
}
```
Using SQLite aggregated functions:
```sql
SELECT 
    COUNT(*), 
    COALESCE(SUM(margin_usdc), 0.0), 
    COALESCE(AVG(item_count), 0.0),
    COALESCE(SUM(execution_fee_usdc), 0),
    COALESCE(SUM(CASE WHEN claimed = 1 THEN execution_fee_usdc ELSE 0 END), 0)
FROM spend_batches
```

### 2. Integration into `HealthResponse` (`/api/health`)
Expose these metrics cleanly in [`HealthResponse`](file:///workspaces/Zeltra-Protocol/nimbus-node/src/dto.rs):
```json
{
  "status": "OK",
  "queued_transactions": 0,
  "processed_nullifiers": 42,
  "relayer_wallet_balance_eth": 0.45,
  "relayer_accumulated_profit_usdc": 18.50,
  "batch_metrics": {
    "batch_count": 12,
    "total_batch_margin_usdc": 18.50,
    "avg_batch_size": 3.5,
    "total_execution_fees_usdc": 25000000,
    "claimed_execution_fees_usdc": 20000000,
    "unclaimed_execution_fees_usdc": 5000000
  },
  "ccip_pending_count": 0,
  "ccip_failure_count": 0
}
```

### 3. Invariants
- **Non-blocking Monitoring:** The aggregate query runs in `task::spawn_blocking` and uses existing SQLite indexes on `spend_batches`.
- **Graceful Fallback:** If `spend_batches` is empty, values default to 0 with no division by zero error (`AVG` returns `NULL`, handled by `COALESCE(..., 0.0)`).
- **Backward Compatibility:** All existing fields in `HealthResponse` remain untouched.
